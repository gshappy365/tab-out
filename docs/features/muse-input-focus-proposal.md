# Muse 对话输入框焦点：复现与适配提案

日期：2026-10-16。状态：用户已批准方案；本地实现、46 项测试与 LCU 核心键入验收完成。详见 [验收记录](muse-input-focus-verification.md)。

## 复现证据

用户反馈 Hark 可直接输入，Muse 未自动获得光标。

LCU 在已安装的本地输入焦点版本及真实 muse.ai 页面观察到：

1. 进入任务时，Muse 已在浏览侧，总览仍在另一侧；AX 存在名为“消息”的文本编辑区域，但没有报告它处于输入焦点。
2. 手动点击“消息”框后，AX 焦点为该编辑区；菜单 → 确定选择 Muse 后，焦点仍恢复编辑区。
3. 在该状态下切换至 Hark，再切回 Muse，编辑区焦点仍可恢复。
4. 点击 Muse 聊天正文使编辑区失焦，再菜单 → 确定选择 Muse，AX 焦点为 Muse HTML content，而非“消息”编辑区。与用户反馈一致。

本轮没有向 Hark/Muse 输入或发送测试消息，也没有保存聊天正文。以上证明的是原生 AX 焦点结果，不是本轮真实网站键入验收。无法仅据此判定 Muse 是否重建 DOM；该内部原因尚未调查。

## 与原需求的区别

原需求只恢复浏览器保留的原输入框，没有输入框焦点时仅聚焦网页。新场景要求 Muse 即使原输入框已失焦，也主动聚焦对话编辑区。

## 建议方案：仅为 Muse 增加可选适配

- 保持其他网站现有焦点策略；Hark 无需专项改动。
- 在已有分屏中，通过总览鼠标点击、确定或成功返回到 https://muse.ai/* 时，先激活真实标签，再定向聚焦可见、可编辑的消息输入区。
- 保留已经存在的编辑焦点和文本选区；不写入文本，不发送消息，不扫描聊天正文，不把输入内容写入 storage 或日志。
- 没有原编辑焦点时，若能准确识别唯一的 Muse 消息输入区，聚焦该区；若发现多个不明确候选，或目标缺失/不可编辑，不猜测，保留浏览侧焦点并提示。
- 适配只在扩展自己的选择/返回操作后短时运行；菜单、遥控方向和日常页面操作不触发持续抢焦点。确切 DOM 定位方式需要在获准后的站点调查中确认，不能仅把 AX 名称当作已验证的 CSS 选择器。
- 显式新增 scripting 能力，并声明可选站点范围 https://muse.ai/*。设置页提供明确开启按钮，由用户为 Muse 授权；未授权时沿用现有行为。
- 不申请所有网站权限，不扩展至 Muse 子域名。

## 验收

先完成隔离测试，再用 LCU 验证 Muse：没有原编辑焦点（例如点击聊天正文后）→ 从总览鼠标选择或遥控确定 → 等待切换完成 → 不额外点输入框即可键入。测试内容不发送；实际键入与清理应避免覆盖用户草稿。

还需验证原草稿、光标/选区、返回、菜单和遥控方向路由、未授权、未找到消息框、Hark 回归。仅模拟命令不等于实体遥控器完整链路验收。
