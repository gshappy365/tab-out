# 分屏选择后将输入焦点交给浏览侧，恢复原输入框

状态：需求已确认，本地实现及隔离测试、LCU 核心输入验收已完成；未发布 Issue。
日期：2026-10-16。
目标仓库：gshappy365/tab-out。
基线：split-screen 分支，Tab Out Remote 1.2.0，提交 18eb41c。

## 问题与目标

当前 1.2.0 从分屏总览选择真实标签后，会主动把焦点交回总览。用户希望选择后立即接着在浏览侧输入，不需要再次点击输入框。

在总览已处于 Chrome 原生分屏时，鼠标点击条目或遥控器确定显示真实目标标签，并把输入焦点交给浏览侧。优先恢复该标签此前正在使用的输入框，尽量保留原光标或选区；没有原输入框时仅聚焦浏览侧，不猜测第一个输入框。

## 已确认行为

1. 鼠标点击条目与遥控器确定采用相同的浏览侧焦点策略；选择已经显示在浏览侧的标签也适用。
2. 遥控器方向命令仍控制总览选中框，不使输入焦点回到总览；普通键盘方向键交给浏览侧，用于移动输入光标。
3. 遥控器返回仍恢复本次首次选择前的起始浏览标签，焦点交给恢复后的标签；恢复原输入框的规则相同。已编辑内容保留，不自动提交。
4. 菜单键呼出或刷新总览时，焦点回到总览。重复菜单不重置分屏选择会话的起点。
5. 只调整已有分屏中的焦点行为。保留 1.2.0 的真实标签身份、原侧位置、跨窗口移动、旧标签保留、返回起点、布局变化处理和配对失败保护；非分屏行为继续按原规则执行。
6. 不自动填入文本、发送表单、选择其他输入框或重新加载网页。

## 权限与可行性边界

> 后续用户已明确批准 Muse 专项例外，见 [Muse 方案](muse-input-focus-proposal.md)及[验收](muse-input-focus-verification.md)。以下不加权限的边界继续适用于其他网站。

第一版不新增 scripting、站点访问权限或内容脚本，也不读取或保存网页输入内容。先停止总览主动抢焦点，并利用 Chrome 对真实标签已有编辑焦点的保留机制验证恢复行为。

“激活浏览侧标签”不等于“原输入框可直接输入”。若实测无法恢复，明确记录具体场景及限制，回到用户讨论按网站授权的方案；不得以标签激活代替输入恢复验收，也不得自行扩大权限。

若目标原输入框已被网页移除、已失去可编辑状态，或页面没有原输入框，只聚焦浏览侧，由用户手动选择输入位置。对特定网站或嵌入式编辑器的支持以实测为准，不承诺任意网页都能恢复。

## 与现有设计的关系

本需求有意调整 split-view-design.md 中“选择后焦点留在总览”的约定；遥控命令继续路由给总览，普通键盘输入则交给浏览侧。

ADR-0003 关于保留真实标签身份的决策继续有效；ADR-0002 关于标签激活与网页输入焦点并不等价的边界继续有效。现有词汇已经足够，不新增通用“焦点”术语到领域词表。

## 实现调查依据

- extension/split-navigation.js 的 focusDashboard 在选择完成后激活总览。
- extension/remote-dashboard.js 收到 remote:show 后还会调用总览 window.focus()，需要区分菜单与选择完成的焦点目的。
- 鼠标 remote:activate 与遥控器 confirm-selection 共用 finishSelection；现有命令路由已能在浏览侧活动时继续控制同一分屏的总览。
- 当前测试主要验证标签身份、布局与草稿保留，尚未证明选择后无需再点击即可输入。

## 验收条件

使用 Chrome 155+ 的隔离环境和 LCU 本机验证，分别覆盖鼠标点击与遥控器确定路径：

- 先在目标标签 B 的输入框输入草稿并放置光标；从总览选择 B 后，不再次点击浏览侧，也不通过测试脚本调用 focus，直接键入唯一标记。只有 B 原输入框按预期增加文字，原草稿保留。
- 在多输入框页面，恢复此前使用的输入框，不能改成第一个输入框；检查中间光标和文本选区的实际恢复结果。
- 目标 B 已在浏览侧时，再次选择它也可直接输入；无原输入框时仅浏览侧获焦，不擅自选框。
- 普通键盘方向键移动输入光标；遥控器方向命令只移动总览选中框，随后确定能更换浏览侧并继续输入。
- A → B → C 连续选择后，返回恢复 A，焦点交给 A，并验证有原输入框时可直接续写；B、C 的草稿保持。
- 菜单回到总览，再次选择后浏览侧可输入；重复菜单不改写返回起点。
- 保留左右两侧总览、跨窗口真实标签、配对失败及非分屏行为的回归验证；扩展权限保持不变。

自动化中通过模拟扩展命令验证路由，不等于实体遥控器验收；若未进行实机按键测试，报告中应分别说明。
